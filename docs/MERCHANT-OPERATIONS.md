# Merchant operations and qualification

## Current boundary

Merchant API, workspace, SDKs, sandbox policy enforcement, and operational views run on the existing application/database/worker. Real provider hosted clients are qualification components, **not connected production execution adapters**. The pilot preflight deliberately fails its software qualification gate. Never remove that gate to run a pilot before implementing and verifying the missing dependencies.

## Risk and applications

`/merchant/onboarding` saves draft business information and submits it for review. `/ops/merchants` starts review or requests changes; feedback is merchant-visible. Application version checks reject stale edits. Application status, risk policy, and live scope are separate. Specified live-scope proposals, approval and revocation are available to internal MFA administrators. Approval validates exact non-fictional merchant/account/profile/evidence scope; it does not switch MerchantConfig to production or enable execution. Merchant-specific templates use the existing Requirement store with `scope.audience = "merchant"`, countries and methods. Provider requirements explicitly exclude these templates. The merchant workspace uploads against matching templates using the existing private evidence endpoint, scanner, review, retention, and expiring signed download. Submission freezes exact requirement IDs/versions and an internal audit snapshot. No merchant legal requirements are invented or seeded; an authorized operator must configure them for the actual scope. Next-review dates are mandatory on scope proposals; overdue review blocks scope eligibility at runtime and is visible in operations. Automatic review reminders are not configured.

Risk checks run within the serializable confirmation/dispatch transaction. Each evaluation records policy version, decision, reason codes, and expiry. Holds create cases in the existing PaymentException queue and prevent an attempt from being created. Amount review approval is an append-only decision valid for 15 minutes and only for the exact policy version. It cannot override hard limits, paused execution, restricted methods, missing/expired evidence, or the closed live gate. New policy versions invalidate previous approvals. Only internal operations admins with MFA step-up may change policy or approve a review, and every change requires an audited reason.

Policies reference exact asset keys and integer minor-unit limits. Daily reservations count each intent once on its first reservation's UTC day and remain reserved after failure. This is deliberately conservative, not a model of provider processing capacity or per-attempt charge volume. Concurrent reservations use serializable transactions; PostgreSQL SQLSTATE 40001 and Prisma P2034 are retried at most three times. Unknown/invalid policy fields fail validation. Empty sandbox policies retain previous fictional fixture behavior. Required evidence must be Clean, Accepted, unexpired, undeleted, and owned by the merchant. Unconfigured external screening is not claimed as operational.

Pause new merchant execution at `/ops/merchants`; existing provider withdrawals and contextual registry restrictions provide provider/method/corridor/environment exclusions. Status polling, incoming events, settlement, merchant delivery, and journal work continue. A held Created attempt requires explicit review/resume; do not create a replacement payment to work around it. Existing simulator fallback proves known non-initiation, not a real provider outage.

## Provider qualification record

Sources checked 2026-09-20:

- [Paystack transaction initialization and verification](https://paystack.com/docs/api/transaction/): hosted requests restrict `channels`; verification checks reference, exact amount, NGN, actual method, and test domain.
- [Paystack webhook contract](https://paystack.com/docs/payments/webhooks/): raw-body HMAC-SHA512.
- [Flutterwave Standard](https://developer.flutterwave.com/docs/flutterwave-standard-1) and [payment methods](https://developer.flutterwave.com/docs/payment-methods): per-payment options require the appropriate account dashboard setting; verify that setting and the observed checkout before qualification.
- [Flutterwave transaction lookup](https://developer.flutterwave.com/reference/verify-transaction-with-tx_ref) and [v3 webhook contract](https://developer.flutterwave.com/docs/webhooks): the implemented boundary uses the documented shared `verif-hash` and requires authoritative lookup before financial effects.

`lib/payments/providers/hosted.ts` uses fixed provider origins, pinned public DNS, an eight-second deadline, bounded response size, exact numeric JSON source text on Node 24, no redirects, and no automatic write retry. It only accepts test credentials. It returns hosted customer action separately from confirmation; non-confirmed/failed lookup remains Unknown. It never invents simulator responses. Flutterwave status requires the configured account ID. Paystack requires test-domain evidence but still needs externally verified credential-to-account binding before activation.

Verified locally: request shape, method preservation parameters, response context/amount/method checks, webhook helpers, and conservative uncertainty behavior. **Not verified:** provider sandbox account eligibility, real hosted behavior, account dashboard settings, settlement/report mapping, provider limits/fees, account contractual platform use, production secret manager, or live execution. No provider network request or financial action was made by these tests.

Remaining integration work: extend the existing execution adapter contract and worker to use real hosted actions/status and provider-specific inbox verification; persist trusted customer contact context; implement account-specific quotes/economics, settlement retrieval and report mapping; qualify idempotency/unknown recovery without assuming that missing lookup proves non-initiation. The simulator remains the only orchestrator execution adapter. Dispatch, fact application, polling and simulator settlement explicitly resolve the immutable integration; an unknown/unqualified real adapter cannot fall through to simulated confirmation or settlement. Do not register these qualification clients as production-ready adapters.

## Pilot preparation

Proposed functional batch: four NGN bank-transfer payments through Paystack, four through Flutterwave, and four hosted-card payments through the approved route. Planning placeholder: NGN 100.00 each (NGN 1,200.00 principal), plus a proposed NGN 300.00 maximum fee allowance, total NGN 1,500.00. These amounts are **unverified and unapproved**; account-specific minimums, fees, permitted testing behavior and participant consent must be verified before presenting the final executable budget. Do not initiate a charge from this placeholder.

`docs/pilot-plan.example.json` contains twelve explicitly unapproved placeholders; `docs/PILOT-PREFLIGHT.json` records the blocked local dry run and zero financial actions. `npm run pilot:preflight -- /path/to/plan.json` is read-only and returns exit code 2 when blocked. Required plan fields: merchantId, operatorId, participantConsentEvidence (IDs), settlementDestinationEvidence, approvalEvidence, webhookEvidence, retentionEvidence, refundRunbook, budgetMinor, feeBudgetMinor, and transactions (reference, integrationId, method, amountMinor). The plan uses NGN minor units. Evidence must already exist in the private organization store. The tool reports missing configuration and the explicit incomplete software gate; a JSON plan cannot authorize execution or manufacture qualification.

Before a live pilot: identify the real merchant and provider account owners; verify settlement destination and permitted platform arrangement; configure production secrets, sender, scanner, public provider webhook endpoints, signed merchant endpoint, retention, scope, exact amounts, fee budget, consent, named operator, and refund/dispute process. Use a separate pilot environment/database and preserve all pilot records. Mark pilot intents server-side using pilotBatchId; general execution analytics exclude them. Never reseed a pilot database.

Collect intent/session, selected method, availability version, route/attempt, provider reference, payment evidence, merchant event/delivery, settlement allocation/evidence, reconciliation result, journal references, dashboard visibility, and exceptions. Existing worker reconciliation can continue after the browser/session ends. Pending settlement remains pending; no successful end-to-end claim until settlement and reconciliation evidence is complete. Twelve payments establish functionality, not a statistical reliability guarantee.

Refund/dispute ownership remains with the authorized provider account owner. Use their verified provider process, retain reference/evidence, reconcile the outcome, and append corrections through the existing journal reversal workflow. No dashboard refund, arbitrary payout, force-success, or mark-settled action is provided.

## Expansion

PublishedProfile.rollout extends the existing registry projection. Production defaults closed. The gate checks stage, merchant allowlist, evidence references, and exact per-transaction maximum within the already direction-specific profile. Paused/Candidate combinations are excluded; limited stages require allowlisting. Existing sandbox profiles with no rollout data retain fixture behavior. There is no new registry or routing engine.

The stage schema supports Candidate, Sandbox qualified, Pilot enabled, Limited live, Generally enabled, Paused. `/ops/coverage` now provides version-checked, audited transitions. Progression cannot skip stages; paused profiles restart at Candidate. Each active stage requires named gate proofs backed by current Accepted/Clean evidence and a next review within 90 days. The implemented software qualification permits only explicitly labeled fictional simulator qualification backed by matching recent Passed sandbox runs. Real-provider and live stages reject with REAL_EXECUTION_AND_SETTLEMENT_QUALIFICATION_INCOMPLETE. Availability rechecks proof ownership, expiry, retention and review date; no later market/method is enabled. Do not write a stage directly to the database. Qualify actual provider/account/merchant-country/payer-country/method/operation/input/settlement/network combinations. Stablecoin asset/network finality and mobile operator behavior remain future qualification work.

## Observability and response runbooks

`/ops/observability` requires existing internal MFA access. It shows the one-hour API sample and mean latency, unknown attempts older than five minutes, inbox backlog, delivery states, exception ages, global worker queue counts and a journal balance check. Queue data is explicitly global because Job has no environment column. `lib/merchant/metrics.ts` contains the shared dictionary and recomputed merchant cohort queries. No additional telemetry SDK or warehouse was installed; trace export, full routing/settlement latency histograms and automated alert dispatch remain unconfigured.

| Signal | Owner / severity | Condition | Action |
|---|---|---|---|
| Duplicate execution, tenant leak, unbalanced posting, wrong destination | Named pilot operator + engineering / Critical | Any confirmed occurrence | Pause affected new execution immediately; preserve event/attempt/journal evidence; investigate; resume only after root cause and independent reconciliation |
| Unknown payment | Payments operations / High | Unknown beyond five minutes in pilot | Query authoritative provider state; retain original reference; never blind retry/fallback |
| Provider event backlog | Payments operations / High | Oldest pending inbox > five minutes | Inspect worker health and authentication; retry durable processing, never drop events |
| Merchant notifications exhausted | Integration owner / High | Any exhausted pilot delivery | Verify URL/secret/receiver availability, then redeliver same event ID |
| Reconciliation discrepancy | Finance operations / High | Unresolved pilot amount/fee/destination mismatch | Obtain provider report; reconcile exact references; append corrections; no expansion while critical issues remain |
| API errors/latency | Engineering / Medium | Internal 5xx >1% over a measured window with sample count shown | Split platform errors from policy/business/provider outcomes; examine redacted request IDs and worker/database health |
| Stale availability/publication | Provider operations / High | Required observation expired or publication not acknowledged | Refresh trusted observations; preserve exclusions until current evidence exists |
| Settlement delay | Finance operations / High | Beyond verified provider/account schedule | Retrieve settlement/report evidence and investigate; payment confirmation alone does not close the incident |

No alert automatically refunds or moves funds. Initial internal goals: zero duplicate execution, unbalanced postings, or tenant leakage; every pilot payment traceable; no critical unresolved discrepancy before expansion; at least 99% successful internal handling of valid requests over the observed pilot window. These are engineering goals, not customer promises.


## Specified live-scope review

`/ops/merchants` accepts a strict JSON scope proposal while an application is Under review or already Approved. Proposals name production, Nigerian merchant/payer geography, NGN input/settlement, bank-transfer/card methods, exact integer transaction/daily limits, published profile IDs, provider integration/account references, account-permission/destination/refund-responsibility evidence IDs, merchant evidence IDs and nextReviewAt (within one year). The initial schema deliberately has no wildcard markets, arbitrary tokens, payouts or pooled platform-account model.

Proposal and approval use optimistic versions. Approval rejects fictional merchants, illustrative/provider-only requirements, missing frozen merchant requirements, mismatched application scope, expired/deleted/unscanned/unaccepted evidence, non-owned integrations, unbound provider account references, and nonmatching published production profiles. It preserves the reviewed scope and actor in the existing internal audit. Revocation and risk pause remain separate from application status. Revising a scope returns it to Proposed; it cannot silently retain approved execution eligibility.

Production availability checks the current approved scope against payer/merchant country, method, exact input and settlement asset, profile, amount, evidence and review deadline. Pre-execution risk also applies scope transaction and atomic aggregate limits. Existing hard software gates continue to deny all live execution. These controls must not be described as evidence that a real adapter or account has been qualified.

Rollout is an operational restriction stored on the existing PublishedProfile. The database still rejects changes to its approved capability, integration, submission and publication fields; only current/rollout can change. Every service-level rollout transition requires internal admin step-up, a reason and an audit entry. Republished profiles receive a new rollout candidate rather than inheriting qualification from an older approved definition.
