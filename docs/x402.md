# x402 on NEAR

PayRouta speaks [x402](https://github.com/x402-foundation/x402) v2 with the `exact` scheme on NEAR (`specs/schemes/exact/scheme_exact_near.md`). The buyer signs a NEP-366 `SignedDelegateAction` for one NEP-141 `ft_transfer`. PayRouta's relayer wraps it in a transaction and pays the gas, so the buyer needs no NEAR. That makes PayRouta a NEP-366 meta-transaction relayer, restricted to exactly this action.

Verification and settlement are the x402 Foundation's own code (`@x402/near` 2.31.0). It checks:

- the signature (ed25519 or secp256k1);
- exactly one `ft_transfer`, to `payTo`, for exactly `amount`, with 1 yoctoNEAR attached;
- the expiry window, mapped from `maxTimeoutSeconds` to `max_block_height`;
- replay, through the access-key nonce;
- that the key is full-access;
- the payer's balance and the recipient's NEP-145 storage.

It also deduplicates concurrent settlements, and reports success only once the inner `ft_transfer` receipt has succeeded on chain.

Two ways in:

1. **Facilitator API** (`app/api/v1/x402/[action]/route.ts`). A merchant running its own x402 server sends payments here, authenticated with a PayRouta API key. Test-mode keys settle on NEAR testnet; live keys settle on mainnet.
2. **Payment links and invoices over x402** (`lib/x402/checkout.ts`). Any x402 client pays a live PayRouta link in USDC on NEAR. The merchant settles in whatever they chose, through NEAR Intents.

## Facilitator API

| Call | Scope | What it does |
| --- | --- | --- |
| `GET /api/v1/x402/supported` | payments:read | `{ kinds: [{ x402Version: 2, scheme: "exact", network }], signers: { network: [relayer] } }` |
| `POST /api/v1/x402/verify` | payments:write | `{ x402Version, paymentPayload, paymentRequirements }` → `VerifyResponse` |
| `POST /api/v1/x402/settle` | payments:write | The same; submits the payment → `SettleResponse` |
| `GET /api/v1/x402/settlements` | payments:read | The business's last 100 settlements, with explorer links |

Every call sends `Authorization: Bearer pr_…` and `PayRouta-Environment`. `@x402/core`'s `HTTPFacilitatorClient` works unchanged when `createAuthHeaders` returns those two headers for `verify`, `settle` and `supported` (see `scripts/demo-x402-near.ts`).

Limits:

- 60 verify and 60 settle calls a minute per business;
- at most 100 Tgas sponsored per payment (the library default);
- the requirement's network must match the key's environment.

Every settle is recorded in `X402Settlement` (source `facilitator`).

## Payment links and invoices over x402

```
GET /api/agent/v1/x402/links/{slug}
GET /api/agent/v1/x402/invoices/{slug}
```

**Without `PAYMENT-SIGNATURE`:**

1. PayRouta opens a checkout for the link, as the Pay button does.
2. It takes the agent-API pay path with origin USDC on NEAR (`nep141:17208628…`) and the relayer as the refund address. This is the same exact-output 1Click quote a customer paying from NEAR gets.
3. It answers `402` with `PAYMENT-REQUIRED`:
   - `exact` on `near:mainnet`;
   - asset: USDC;
   - amount: the quote's `amountIn`;
   - `payTo`: the quote's deposit address, a 64-hex implicit NEAR account;
   - `extra`: the checkout id and token.

**With `PAYMENT-SIGNATURE`:**

1. PayRouta reads the checkout from `extra`, authorizes it with the token, and rebuilds the requirement from the stored quote, never from the payload.
2. It registers the deposit address with USDC storage from the relayer (0.00125 NEAR) if needed, then verifies and settles.
3. It records `X402Settlement` (source `checkout`) and tells 1Click about the deposit.
4. It answers `200` with `PAYMENT-RESPONSE`.

From there NEAR Intents delivers to the merchant, and the checkout confirms through the normal cross-chain pipeline. An agent key (`Bearer pra_…`) is held to its limits, because the 402 goes through `pay()`.

The link terms (`GET /api/agent/v1/links/{slug}`) list `{ method: "x402", url }` when the link is live and a mainnet relayer is configured.

Live only: 1Click has no testnet.

## Configuration

| Variable | Meaning |
| --- | --- |
| `X402_NEAR_MAINNET_RELAYER` | Relayer account on mainnet. 1Click refund addresses need 20–140 characters, so use an implicit account or a long name. |
| `X402_NEAR_MAINNET_RELAYER_KEY_REF` | Secret-store reference to its full-access key (`ed25519:…`) |
| `X402_NEAR_TESTNET_RELAYER`, `X402_NEAR_TESTNET_RELAYER_KEY_REF` | The same on testnet |
| `NEAR_RPC_URL`, `NEAR_TESTNET_RPC_URL` | Optional RPC overrides (default FastNEAR) |

Production gets these from GitHub:

- **Variables:** `X402_NEAR_MAINNET_RELAYER` and `X402_NEAR_TESTNET_RELAYER`.
- **Secrets:** `X402_NEAR_MAINNET_RELAYER_KEY` and `X402_NEAR_TESTNET_RELAYER_KEY`. `deploy.yml` stores each key in the secret store and keeps only its reference.

Without a relayer, that network isn't offered.

## Verified

The end-to-end run on NEAR testnet (`npm run demo:x402-near`, 13 November 2026):

- A merchant's x402 server, built on `@x402/core`'s `x402ResourceServer` and `HTTPFacilitatorClient`, pointed at PayRouta's route handlers.
- An agent paying with `@x402/fetch` and `@x402/near` from `payrouta-agent.testnet`, with spend controls limited to pUSD and a 1.00 cap.
- `payrouta-relayer.testnet` relaying. 0.10 pUSD (`payrouta-test-usd.testnet`) went from the agent to `payrouta-merchant.testnet`, for example tx `FZW3mwyZnQX4VaCNxKhAMkQViiBdLBc3ToiMDWQ84P1v`.
- The same signed payment sent again was refused: `invalid_exact_near_payload_delegate_action_nonce_already_used`.

The mainnet link path ran with real funds on 13 November 2026:

- An agent account paid the $1.00 live link `BgKcFgkGUG` with `npm run x402:pay`. The payment was 1.010669 USDC on NEAR, settled by the relayer `de121cb4…6cdc` in tx `2kb8WX7gzoPwh64gMxjRa5sGpt2GSfoNYBaTszANJU8S`. The relayer also registered the deposit address's storage.
- 1Click delivered 0.985451 USDC to the merchant's NEAR Intents account in tx `CXUWYHKhQs8SE1BWaaMn2SVGvcii9TJnZwiT5Kv1QLh5`.
- PayRouta confirmed and settled it: gross 1000458, fee 15007, net 985451, an exact match.
- Confirmation first waited behind a reconcile backlog. Fixed in `df146c7`: reconcile expects the fee withheld at source.
